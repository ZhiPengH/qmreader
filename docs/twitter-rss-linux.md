## 1. 已确认目标与边界

- 日常在纵览News 粘贴 `https://rsshub.app/twitter/user/zaobaosg`、`https://rsshub.app/twitter/user/waylybaye` 这类链接，不更换域名，不为每个订阅手工配置取数服务。
- 保留现有「预览 → 确认订阅」流程。预览展示真实源标题、有效条目数量与最新条目；确认后由服务器保存并抓取。
- 使用用户自己的 X 登录凭据。用户尚未指定具体账号；不能据此读取浏览器 Cookie、假定使用主账号或要求把凭据贴进聊天。
- 常用约 50 个 X 账号，设计与容量验收覆盖最多 100 个。优先不购买 X 开发者 API，复用现有懒猫 Linux / Docker；免费软件不等于没有网络、维护或账号风险。
- 更新延迟目标不超过 2 小时。衡量对象是正常可访问的公开新帖从发布时间到首次入库的延迟，不是任务启动间隔或 RSS 的构建时间。
- 账号认证、取数、RSS 解析、去重、调度和持久化全部在 Linux。Mac/iPhone 不承担后台抓取；普通 RSS 与现有阅读、收藏行为保持。

两小时是正常取数条件下的验收目标，不是上游故障时的无条件保证。凭据失效、X 限流、接口变动或网络不可达时必须展示异常；不能把延期静默写成达标。单个登录状态能否持续服务 50–100 个账号尚未实测，容量不达标则回到方案评审，不私自放宽目标、购买服务或扩充账号池。

本轮不做：付费 API 接入、多账号轮换、所有 RSSHub 路由统一迁移、X 搜索/列表订阅、私密及付费内容获取、全量历史回补、公开 RSSHub 服务、前端账号管理面板、视频下载或 AI 内容处理。RSS 返回的文字、链接及媒体信息复用现有阅读能力；媒体离线镜像不是本轮范围。

## 3. 选定架构

逻辑链路：原始 RSSHub 链接 → 纵览 Linux 后端识别 → 内部 RSSHub 取数 → 标准 RSS 解析 → 现有 SQLite/文章缓存 → Mac/iPhone 阅读。

### 服务部署

- 新增独立 RSSHub 服务，不把抓取代码塞入前端或 Hermes 插件。使用轻量官方镜像；实际版本经过验证后固定镜像 digest，并记录对应源码版本，不自动追 `latest`。
- RSSHub 与 qmreader 通过专用 Docker 网络通信；RSSHub 不发布公网端口，不新增面向手机的 RSSHub 域名，不修改懒猫现有访问保护。容器间使用服务名，不使用彼此的 `127.0.0.1`。
- Docker 网络需允许 RSSHub 合法出网；「不向外发布端口」不等于禁止出网。是否需要代理由 Linux 容器到 X 的实际请求决定，不套用 Mac 浏览器的连通性。
- X 凭据仅注入 RSSHub。服务器专用配置文件由用户持有、权限限制为 0600，并排除 Git、源码打包、客户端接口及普通日志。该文件权限保护不等于加密。凭据撤销/替换后要重新验证取数，不能只重启后查看健康页。
- 首轮采用单 RSSHub 实例和内存缓存，不预先增加 Redis、浏览器容器或新的采集数据库；重启后错峰恢复，避免缓存清空导致请求齐发。若容量实测证明需要持久缓存，再明确调整方案。
- RSSHub 服务自己的 Compose/凭据配置与 qmreader 配置分开管理；共享网络归属写进双方 Compose。常规 News 发布只更新 News，不覆盖 RSSHub 凭据或重建其服务。

### 服务端透明转接

- 以已知 RSSHub 域名和精确 Twitter 用户路由判断是否接管；不得通过域名包含字符串、任意重定向或任意内网 URL 推断为受信服务。
- 继续存储稳定的逻辑地址（现有 `{rsshub}/twitter/user/...`）及原 source ID。对已保存的公共形态也应用同一识别；不为换通道重建订阅、迁移文章或丢失收藏。
- 由服务端配置生成内部目标。拟新增的内部 RSSHub 地址配置属于部署配置，不允许客户端请求指定或覆盖；具体配置名在实现时统一，本文不把它写成现成配置项。
- 预览、创建/编辑校验、批量导入富化、首次抓取、周期刷新及手动刷新使用同一解析规则。普通 RSS、非 Twitter 的 RSSHub 路由以及内置特殊适配器保持原逻辑。
- 合法且本轮支持的路由参数保留；不支持的参数明确拒绝，不悄悄换语义。对用户名、路径、编码分隔符和参数做严格校验，不能拼接为任意内部请求。
- 内部抓取使用独立的受限请求路径：限定服务 origin、端口与 Twitter 路由，禁止重定向逃逸；保留超时、响应大小及 XML 安全检查。普通公网抓取仍保留 DNS 固定、重定向与私网阻断。
- Twitter 私有通道不可用时给出真实错误，不自动轮询公共实例、伪装游客抓取成功或切换付费通道。内部地址、令牌及上游敏感原始错误不返回前端。

## 4. 50–100 个账号的调度方案

以下是待实测的工程初值，不是已证明的 X 配额或安全阈值。

| 项目 | 拟采用策略 |
| --- | --- |
| 正常周期 | 每个 Twitter 源约每 60 分钟进行一次服务端刷新，与用户给源选择的分类无关 |
| 错峰 | 将源分散到周期中；启动、导入及服务恢复不一次向 X 发出全部请求 |
| 缓存 | RSSHub feed 缓存初值 15 分钟；确认所选版本的相关内部缓存行为，不能仅改外层缓存后假定已请求上游 |
| 后台并发 | Twitter 后台先从串行开始；与普通 RSS 区分并发预算，实测后再决定是否调整 |
| 预览与手动刷新 | 同源请求合并、复用短时缓存并限制交互并发；不提供绕过上游缓存或限流的强制刷新 |
| 忙时处理 | 待刷新源留在去重待办中，worker 完成后继续排程；不能沿用“正在忙就跳过”且无后续保证的行为 |
| 公平性 | 按到期与等待时间处理，普通源保留执行机会；一个错误源不能占满整个队列 |
| 错误退避 | 复用现有失败状态；明确限流时尊重可获取的重试时间，认证失效时停止无意义的密集重试 |

复用现有后台 worker 与存储链路，只补足 Twitter 到期规则、待办及执行容量，不引入独立任务平台或另一套定时抓取数据库。启动刷新、每日全量、点击源、手动刷新和预览都要核对，防止日常任务绕开节流或重复挤占额度。预览与 worker 不同进程，不能仅凭单进程并发参数声称全链路串行。

容量计算（仅 feed 层，已用 Python 计算）：

- 源码默认每 5 分钟最多选 3 源，稳定扫描额度约 36 源/小时、72 源/两小时，尚未扣除其他 RSS 和 worker 忙碌。100 个账号不能照搬这一容量。
- 每账号每小时一次，对应 50 或 100 次 feed 请求/小时，即 1,200 或 2,400 次/日；不含预览、重试等额外请求。
- 一次 feed 请求可能产生多个 X 内部请求，不能把上述数字当成 X API 请求量，更不能据此保证单账号足够。

**时效与完整性分开验收：**轮询频率不等于真实新帖延迟。记录帖子原始 ID、发布时间、首次入库时间，实际验证不超过两小时；请求成功但反复返回旧数据不能证明达标。同时检查上游返回的最近窗口能否覆盖高频账号（尤其 `zaobaosg`）的周期发帖量，取回的有效条目不得再被普通源默认 20 条静默截掉。本轮不承诺无限翻页或全量历史；窗口不足或缺口无法补齐要报告，并在继续扩容前调整方案。

## 5. 成功、等待与失败的用户语义

- **预览成功**：返回有效 RSS 且存在可用条目，展示真实标题、条目数和最新条目。初次空 RSS 提示「未取得有效内容」，不直接进入成功态；不把它断言为账号失效或作者停更。
- **确认订阅**：先显示「已保存订阅，正在首次抓取」；只有有效条目写入并可从列表读取后才显示就绪。预览成功不替代入库验收。
- **已有订阅失败**：保留文章、收藏与订阅；显示等待、限流、认证/服务异常等有证据的状态。能可靠识别什么就显示什么，不能从空结果反推具体原因。
- **时间信息**：区分最近尝试、最近有效 feed 获取和最新帖子的发布时间。上游没有暴露真实取数时间时，不能命名为「最近向 X 验证成功」。作者暂未发帖与采集停摆也不能仅凭帖子年龄区分。
- **两小时目标未满足**：缺少近期有效检查时显示抓取延迟/异常；有独立新帖证据而本地缺失时记为时效失败。只拿到非空旧 RSS 不能自动诊断“正常”，也不能无证据判成“断更”。
- **恢复**：修复凭据或网络后沿原 source ID 继续，按帖子链接/ID 去重，不清库、不要求重新添加所有订阅。

## 6. 获得实施授权后的顺序与停点

### A. 先证明实际取数与容量

1. 只读核对 Linux 实际容器、网络、现有配置及所选 RSSHub 版本；不沿用历史环境快照。
2. 在独立服务配置中安全提供 X 登录凭据，验证容器实际出网；不读取或复制用户其他浏览器会话。
3. 先测试两个示例账号：有效 XML、非零条目，ID/链接/发布时间可对应到真实帖子。
4. 跨过缓存周期，等待公开账号产生可核对的新帖，确认获取新增内容；HTTP 200、`lastBuildDate` 变化和容器健康均不替代此项。
5. 再使用用户实际提供的账号清单逐步扩到约 50 个；需要证明 100 个容量时取得对应清单。建议持续观察至少 24 小时，记录各源有效刷新间隔、已核对新帖延迟、限流和高频源窗口；观察时长是工程建议，不是已经验收。

**停点：**无法取得真实新帖、出现不可解释的空结果/旧数据或容量不足时，先报告证据。不得继续宣称原版 RSSHub 已适用；若必须修补 RSSHub 上游代码或换付费/多账号路线，另列影响并确认，不把维护 fork 偷偷并入本轮。

### B. 最小接入与回归

1. 先写失败测试，覆盖同一输入在预览/校验/后台刷新走不同实例、内部目标被公网防护拒绝、空 feed 被误报成功等实际缺口。
2. 实现共享路由判断和限定的内部请求，保持普通 RSS 防护与现有持久化。
3. 补 Twitter 到期调度与待办，用可控时钟测试 50/100 源、worker 忙碌、失败退避、恢复和与普通源并存。模拟测试可以证明排程，不可冒充 X 容量实测。
4. 验证首次入库、重复请求、编辑/导入、手动刷新和原 source ID 恢复；覆盖默认条数截断及已有阅读状态保留。
5. 隔离数据运行相关测试和全套 `npm test`，保留真实日志与退出码；页面检查在 4178，不能让本地验证无意连到生产凭据或生产数据库。

### C. 明确部署授权后才接入正式环境

1. 单独审阅并备份需要变更的 Compose、网络和凭据配置；不覆盖现有 `.env`/数据，备份同样限制访问权限。
2. 配置好内部通道后，按现有 `ops/news/deploy.sh` 发布 News 源码；原脚本不能代替新增服务配置的上线。
3. 通过原始公共形态链接完成预览、订阅、真实入库、后续新帖检查及 Mac/iPhone 阅读。
4. 验证服务重启后订阅、文章和状态保留；异常后恢复不重建订阅、不重复入库。回退时保留数据，不自动恢复旧数据库；撤掉通道也不能把旧 Twitter 公共实例当作可用兜底。

本轮不执行上述阶段；方案确认和文档落盘不构成实施、发布、commit、merge 或 push 授权。

最低验收集：

- 两个示例链接原样可用；普通 RSS 和非 Twitter 路由保持原行为。
- 预览、创建/编辑、导入富化、首次抓取、周期与手动刷新采用同一通道；不依赖浏览器后台运行。
- 任意用户内网 URL、伪造 RSSHub 域名、编码路径逃逸及跨 origin 重定向被拒绝；响应、日志和导出不泄露凭据。
- 空 feed、401/403/429、服务不可达、超时及重复旧内容均不被拿来伪造新帖更新证据；失败保留旧文章。
- 50/100 源排程模拟无饿死，真实目标清单的新帖延迟在正常条件下不超过两小时；模拟与实测分别标记。
- 原 source ID、查重、收藏和服务重启后状态保持；两端实际页面验收，不用全套测试通过替代。
